1. EXECUTIVE SUMMARY & OBJECTIVES
--------------------------------------------------------------------------------
This milestone successfully implements and verifies the AI Call Decision Engine
for the AI Calling Agent system. The engine bridges the caller pre-screening
service (which gathers context from Supabase tables: contacts, priority contacts,
spam cache, call history, and user preferences) with a local Qwen LLM (qwen3:8b)
running via Ollama.

The engine evaluates real-time caller evidence and recommends one of three
definitive triage actions:
  - HANDLE: The AI agent may handle the call according to user preferences.
  - DECLINE: The call may be declined based on reliable evidence and preferences.
  - ESCALATE: The situation requires the user's attention or a human decision.

Key achievements:
  1. Strict multi-tenant security: Authenticated user UUID derived strictly from
     the Supabase JWT Bearer token; client-supplied IDs are never trusted.
  2. Database efficiency: Zero query duplication; reuses get_prescreening_context.
  3. Prompt injection immunity: Untrusted caller metadata isolated within
     anti-tampering XML tags (<caller_evidence>...</caller_evidence>).
  4. Deterministic safety guardrails: Python-level safeguards prevent priority
     contacts from being declined and force escalation when conflicting signals
     are detected (e.g., a priority contact that also appears in spam cache).
  5. Resilient fallback: Any LLM timeout, connection error, or invalid JSON
     falls back safely to ESCALATE with low confidence (0.3).
  6. High performance & low latency: Disabled Qwen 3 internal reasoning tokens
     (think=False) and constrained output tokens (num_predict=150), reducing CPU
     inference latency from over 60 seconds to ~1-10 seconds.
  7. Verification: 100% test pass rate across 43 unit, endpoint, and live tests.

         |      Sends system prompt + evidence to local Qwen 3 (qwen3:8b)

         |-- d. parse_and_validate_decision_json()

         |
         |-- e. apply_deterministic_safety_rules()
         |      Safety Rule: Priority contact declined? -> Override to ESCALATE
         |      Safety Rule: Contact in spam cache? -> Override to ESCALATE
         |

         |      If Ollama times out or fails: Fallback to ESCALATE (confidence=0.3)

4. DECISION RULES, PRECEDENCE, AND SAFETY CONSTRAINTS
--------------------------------------------------------------------------------

Caller Classification Hierarchy:
  When a caller matches multiple criteria, classification resolves strictly as:
  1. PRIORITY_CONTACT (if in priority_contacts table for this user)
  2. KNOWN_CONTACT    (if in contacts table for this user and not priority)
  3. SPAM             (if in global spam_cache table and not in user contacts)
  4. UNKNOWN          (if not found in any contact or spam table)

Triage Decision Actions:
  - HANDLE:
    * Assigned when the caller is a verified regular contact with no negative indicators.
    * Assigned to priority contacts when user preferences explicitly permit AI handling.
    * Assigned to non-threatening unknown callers when screening is allowed.
  - DECLINE:
    * Assigned when the number appears in the spam cache with no conflicting signals.
    * Assigned when user preferences explicitly mandate declining (e.g. unknown callers).
    * MUST NEVER be assigned to a priority contact.
  - ESCALATE:
    * Assigned when a priority contact calls and personal attention is needed.
    * Assigned when conflicting evidence exists (e.g. contact also listed in spam cache).
    * Assigned when user preferences are ambiguous, contradictory, or demand escalation.
    * Assigned as safe fallback whenever LLM inference fails, times out, or emits invalid JSON.

Deterministic Python Guardrails:
  1. Priority Contact Escalation & Protection:
     - Priority contacts default to ESCALATE because callers (Family, Work, VIP) require direct human attention.
     - If the model outputs DECLINE for a priority contact, Python safety rules override to ESCALATE:
       "Priority contacts are protected from automatic decline. Escalating for user attention."
     - If the model outputs HANDLE for a priority contact without an explicit user preference specifically
       authorizing AI handling, Python safety rules override to ESCALATE:
       "Priority contacts require direct user attention and must be escalated unless an explicit preference permits AI handling."
  2. Conflicting Signals Override:
     If a number exists in contacts or priority contacts AND also exists in spam_cache,
     Python safety rules override the decision to ESCALATE with reason:
     "Conflicting signals: Caller is present in user contacts but also listed in spam cache. Escalation required."
  3. Safe Fallback:
     If JSON decoding fails or Ollama encounters an exception, decide_call returns:
     decision=ESCALATE, confidence=0.3, caller_type=deterministic_type.

    {"detail": [{"loc": ["body", "caller_phone_number"], "msg": "Field required"}]}
  - 500 Internal Server Error:
    {"detail": "Failed to retrieve caller pre-screening information. Please try again later."}
